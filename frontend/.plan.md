# S15P11A406-28 닉네임 입력 설계안

> 상태: 구현 완료  
> 범위: 닉네임 입력, 빈 입력 시 자동 생성, 검증, 임시 저장  
> 구현 기준: 2026-07-23 확정 결정
>
> 2026-07-23 결정: 닉네임 중복을 허용하며 인증·권한 판단에는 사용하지 않는다. 최신 결정은 `docs/determined.md`를 따른다.

## 1. 목표

- 사용자가 닉네임을 직접 입력할 수 있다.
- 입력하지 않아도 흐름이 막히지 않고 센스 있는 임시 닉네임으로 입장한다.
- 화면과 코드에서 직접 입력과 자동 생성의 처리 경로가 하나로 읽힌다.
- 길이와 허용 문자 제한의 최종 판단은 서버가 담당한다.
- 계정 없는 빠른 입장이라는 제품 방향을 유지한다.

관련 요구사항은 `ENT-NICK-001`, `ENT-NICK-002`, `ENT-NICK-003`이다.

## 2. 사용자 경험

### 화면

- 제목: `어떤 이름으로 참가할까요?`
- 화면 진입 시 추천 닉네임을 한 번 만들고 입력란의 placeholder로 보여준다.
- 안내 문구: `비워두면 {추천 닉네임}(으)로 입장해요.`
- 기본 버튼 문구: `대기실 입장`
- 입력값 앞뒤 공백을 제거했을 때 빈 문자열이면 화면에 표시한 추천 닉네임을 제출한다.
- 생성된 닉네임은 별도 확인 단계를 추가하지 않고 그대로 입장에 사용한다.
- 입장 성공 후 대기실의 내 참가자 카드에서 부여된 이름을 즉시 확인할 수 있다.

### 예시 이름

닉네임은 `형용사 + 명사` 두 단어를 띄어 써서 만든다.

- 느긋한 주사위
- 수상한 선장
- 용감한 펭귄
- 졸린 해적
- 신나는 문어
- 재빠른 갈매기

단어 목록은 YORR의 바다·항해·주사위 분위기를 중심으로 구성한다. 조롱, 외모 평가, 성별, 정치·종교처럼 불편함을 만들 수 있는 표현은 넣지 않는다.

## 3. 입력 정규화와 검증

처리 순서는 아래 하나로 고정한다.

```text
원본 입력
  -> 앞뒤 공백 제거
  -> 비어 있으면 자동 생성
  -> 클라이언트 기본 검증
  -> 입장 요청
  -> 서버 최종 검증
```

클라이언트 검증 제안:

- 앞뒤 공백은 제거한다.
- 연속된 내부 공백은 한 칸으로 합친다.
- NFC 정규화 후 공백을 포함해 1~12자로 제한한다.
- 유니코드 문자, 숫자, 한 칸 공백만 허용한다. 이모지와 특수문자는 허용하지 않는다.
- 닉네임 중복은 허용한다.

길이와 허용 문자 규칙은 백엔드와 동일한 계약으로 확정해야 한다. 서버와 다른 정규식을 프론트에 별도로 만들지 않는다.

### 공통 텍스트 입력과 XSS 방어

- 별도 HTML purification 라이브러리나 Zod는 도입하지 않는다.
- 공통 `TextField`는 `label`, `value`, `helpText`, `errorMessage`와 기본 input 속성을 받아 여러 화면에서 재사용한다.
- 오류가 있으면 `aria-invalid`와 `aria-describedby`로 입력란과 오류 문구를 연결하고, 오류 문구에는 `role="alert"`를 적용한다.
- 입력 검증은 도메인 규칙을 안내하기 위한 것이며 XSS 방어 자체로 간주하지 않는다.
- 사용자 문자열은 React 텍스트 보간으로만 렌더링하고 `dangerouslySetInnerHTML`이나 HTML 문자열 삽입에 사용하지 않는다. React의 기본 escaping을 우회하지 않는다.
- 정규화·검증은 라이브러리 없이 작은 순수 함수로 구현하고, 서버에서도 같은 제한을 다시 검증한다.
- 공통 컴포넌트가 값을 몰래 삭제하거나 바꾸지 않는다. 닉네임 화면이 제출 시 정규화하고 검증 결과를 `TextField`에 전달한다.

## 4. 자동 닉네임 생성

### 구조

```ts
const adjectives = ['느긋한', '수상한', '용감한'] as const
const nouns = ['주사위', '선장', '펭귄'] as const

type GeneratedNickname = `${(typeof adjectives)[number]} ${(typeof nouns)[number]}`
```

- 생성기는 네트워크나 React에 의존하지 않는 순수 함수로 둔다.
- `src/`의 기존 단층 구조를 지키며, 실제 구현 시 재사용 범위에 따라 `src/nickname.ts` 또는 닉네임 화면 파일 내부에 둔다.
- 단어 배열의 모든 조합이 길이 제한을 통과하도록 작성 시점에 관리한다.
- 암호학적 난수는 필요하지 않으며 `Math.random()`으로 충분하다.

### 추천 이름 수명

- 추천 이름은 화면에 처음 진입할 때 한 번만 생성한다.
- React 재렌더링이나 입력 수정 때마다 추천 이름을 바꾸지 않는다.
- 입력이 비어 있으면 placeholder와 안내 문구에 표시한 동일한 이름을 제출한다.
- 사용자가 직접 입력하면 추천 이름은 제출값에 영향을 주지 않는다.

## 5. 임시 저장

- 입장에 성공한 닉네임만 `sessionStorage`에 저장한다.
- 같은 탭에서 새 방에 입장하거나 새로고침할 때 저장값을 입력란의 초깃값으로 제안한다.
- 저장소 접근이 차단되거나 예외가 발생해도 입장 흐름은 계속 진행한다.
- 로그아웃 개념이 없는 MVP이므로 영구적인 `localStorage` 저장은 사용하지 않는다.
- 서버가 재접속 세션을 복원하면 저장된 닉네임보다 서버 스냅샷의 닉네임을 우선한다.

## 6. 상태와 책임

닉네임 입력값과 검증 메시지는 화면의 로컬 상태로 둔다. 전역 Zustand store에는 입장 성공 후 서버가 돌려준 세션과 스냅샷만 저장한다.

```text
NicknamePage
  draftNickname     사용자가 편집 중인 값
  validationMessage 로컬 검증 메시지
  joinTask           요청 중/성공/실패 상태

AppStore
  roomSession        입장 성공 후 세션
  roomSnapshot       서버가 확정한 내 닉네임과 참가자 목록
```

자동 생성 여부는 요청 처리 과정에서만 필요하므로 전역 상태로 저장하지 않는다.

### 재접속

- 유효한 `sessionToken`이 있으면 닉네임을 다시 입력받지 않고 WebSocket 재접속을 요청한다.
- 재접속 성공 시 서버 스냅샷의 닉네임과 참가자 상태를 그대로 사용한다.
- 세션이 만료됐거나 서버가 복구를 거절한 경우에만 신규 입장 흐름으로 돌아간다.

## 7. 방 입장과 통신 계약

### 진입 경로

코드 입력, QR, 초대 링크는 모두 같은 입장 흐름을 사용한다.

```text
코드 직접 입력 -> roomCode 확인 -> 닉네임 확인
QR/초대 링크   -> query string의 roomCode 확인 -> 닉네임 확인
```

QR과 링크는 방 선택 기능이 아니라 코드 입력 단계를 생략하는 단축 경로다. 유효하지 않거나 만료된 코드라면 닉네임 제출 전에 오류 화면을 보여준다.

### REST와 WebSocket 책임

```text
1. 방 생성자는 REST로 방을 생성하고 roomId/roomCode를 받는다.
2. 생성자는 방 생성 REST에, 참가자는 방 참가 REST에 nickname을 제출한다.
3. REST 입장 응답으로 playerId, sessionToken, snapshot을 받는다.
4. WebSocket 연결 후 sessionToken으로 해당 세션에 연결한다.
5. 이후 참가자 목록과 방 상태는 WebSocket 이벤트와 snapshot으로 동기화한다.
```

- 참가자 생성, 정원 검사, 세션 발급의 단일 책임은 REST 입장 API에 둔다.
- WebSocket은 이미 발급된 세션을 인증하고 실시간 채널에 연결할 뿐 참가자를 다시 만들지 않는다.
- `room.join`은 REST가 발급한 `sessionToken`으로 실시간 채널을 연결한다.
- 첫 연결과 재연결이 같은 `sessionToken` 복구 절차를 쓸 수 있는지는 백엔드와 이벤트 이름·응답을 확정한다.
- 방 생성 API는 참가 세션이 아니라 방 식별 정보만 반환한다.

### 참가자 표시

- 닉네임이 같아도 화면에서 임의 숫자를 붙여 이름을 변경하지 않는다.
- 내 `playerId`와 일치하는 참가자에는 `나` 표시를 붙인다.
- 참가자별 색상이나 기본 아바타는 `playerId`에서 안정적으로 파생해 같은 세션에서 일관되게 보여준다.
- 방장 역할은 구분하지 않으며, 대기실의 모든 참가자가 시작을 요청할 수 있다.
- 서버는 최소 인원과 방 phase를 검증하고 먼저 성공한 시작 요청만 처리한다.

### 서버 오류 처리

- 방 존재 여부, 정원, 시작 여부, 세션 유효성의 최종 판정은 서버가 담당한다.
- 프론트는 서버 오류를 추측해 판정하지 않고 오류 코드에 맞는 안내와 이동만 수행한다.
- 존재하지 않거나 만료된 방은 코드 입력 또는 진입 안내로 돌려보낸다.
- 정원 초과나 이미 시작한 방은 현재 입력값을 보존한 채 입장할 수 없는 이유를 표시한다.
- 연결 실패는 재시도할 수 있게 하고, 요청 중에는 중복 제출을 막는다.

## 8. 예상 구현 범위

계약 확정 후 다음 범위만 구현한다.

- 닉네임 입력 화면과 route
- 코드 입력과 QR/초대 링크 query string을 동일한 입장 context로 변환하는 처리
- 입력 정규화·검증 함수
- label, 도움말, 오류 문구를 제공하는 재사용 `TextField` 컴포넌트
- 형용사·명사 기반 자동 생성 함수
- 직접 입력과 빈 입력을 하나로 처리하는 입장 submit 흐름
- 성공한 닉네임의 안전한 `sessionStorage` 저장·복원
- MSW fixture와 handler의 닉네임 시나리오 갱신

대기실 참가자 UI와 게임 시작 제어는 다음 설계 구간으로 분리한다.

## 9. 검증 계획

순수 함수 단위 테스트:

- 공백 입력이면 허용된 조합으로 닉네임을 생성한다.
- 직접 입력은 자동 닉네임으로 변경하지 않는다.
- 정규화와 길이·문자 검증이 계약대로 동작한다.
- 생성 가능한 모든 조합이 길이와 문자 제한을 만족한다.

사용자 동작 테스트:

- 닉네임을 입력하고 제출하면 그 이름으로 입장을 요청한다.
- 빈 입력을 제출하면 placeholder에 표시한 추천 이름으로 입장을 요청한다.
- 잘못된 입력에는 입력란과 연결된 이유 문구를 표시한다.
- 요청 중에는 중복 제출할 수 없다.
